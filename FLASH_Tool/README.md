# PCAN CAN 上位机

基于 **PyQt5 + python-can** 的 CAN 调试上位机,用于配合 STM32F103 做 CAN 通信的收发调试。

- 自动枚举当前连接的 **PCAN** 设备
- 按需发送 CAN 报文(单条 / 批量 ID / 周期发送)
- 实时监控并记录**收发**报文
- 日志同时输出 **CSV**(可直接看/丢进 Excel)和 **BLF**(可用 PCAN-View 回放分析)

---

## 3. 接线

PCAN-USB 与 STM32 之间只需 **CAN-H / CAN-L 两根信号线 + 共地**:

```
PCAN-USB                    STM32F103
  CAN-H  ────────────────────  CAN_H  (PA11, 复用推挽)
  CAN-L  ────────────────────  CAN_L  (PA12, 复用推挽)
  GND   ────────────────────  GND
```

要点:

1. **两端波特率必须一致**(本工具默认 500 kbit/s),否则会出现 `bus-off` 或大量错误帧。
2. 总线两端各接一个 **120 Ω 终端电阻**。只有两个节点时,一般在**各自**节点附近各焊一个 120 Ω;
   PCAN-USB 多数型号板载终端电阻,用跳线/拨码开关确认是否已使能。
3. STM32 侧 CAN 引脚必须配置成 **复用推挽输出**(AF_PP),并初始化 CAN 外设
   (时钟、位时序、`CAN_Mode_Normal`、收发邮箱与过滤器)。只有引脚模式配错是"发不出去也收不到"最常见的原因。
4. 建议把 PCAN-USB 的 120 Ω 终端电阻**关掉**,只在 STM32 一侧接终端,避免阻值过小(60 Ω)导致波形畸变。

## 4. 界面说明

```
┌──────────────┬────────────────────────────────┬──────────────┐
│  连接与发送   │          报文监控(中央)         │   报文统计    │
│  (左侧可拖动) │  时间 / 方向 / ID / 类型 / DLC  │  (右侧可拖动) │
│              │            / 数据               │              │
├──────────────┴────────────────────────────────┴──────────────┤
│                     系统消息(底部,可拖动)                     │
└─────────────────────────────────────────────────────────────┘
```

三个停靠窗口都可以拖动/浮动/关闭,用菜单 `窗口` 可以重新挂回来。

### 4.1 连接

1. 在 **PCAN 设备** 区点 `刷新`,下拉框会列出所有已连接通道,例如
   `PCAN_USBBUS1 - PCAN-USB (ID 255) - 已连接`。
2. 选 **波特率**(10k ~ 1M)。
3. 按需勾选 **记录收发报文** 与输出格式(CSV / BLF)。
4. 点 **打开通道**。按钮变成 `关闭通道` 即表示连接成功。

> PCAN-USB 不支持 CAN FD,此时 `启用 CAN FD` 会自动置灰。换用 PCAN-USB FD/FD Lite 时可勾选,
> 并单独设置数据段速率。

### 4.2 发送

- **CAN ID**:十六进制,支持 `1A2`、`0x1A2` 两种写法;**一次可以填多个 ID**(用逗号分隔),
  例如 `100,200,300`,回车即依次发出三帧。
- **数据**:支持 `01 02 03 04`、`01020304`、`01,02,03,04` 三种写法,最多 8 字节。
- **扩展帧**:勾选后 ID 范围放宽到 29 位(`0x1FFFFFFF`),否则上限 `0x7FF`,越界会直接报错而不是静默发送。
- **远程帧 (RTR)**:勾选后只发 ID、不带数据。
- `填 0` / `填 FF`:按当前 DLC 长度快速填充数据。
- **周期发送**:设置周期(1 ms ~ 60 s)与次数(0 = 一直发,直到点 `停止`)。
  周期调度跑在独立工作线程里,不受界面卡顿影响。

### 4.3 监控

表格实时滚动显示所有收发报文:

- **蓝色 TX** = 本工具发出,**绿色 RX** = 总线收到,**红色** = 错误帧
- `暂停` 可以冻结表格(后台仍在收、仍在写日志),积压的报文会在点 `继续` 时一次性补上
- **过滤**框输入 ID 或数据关键字即可筛选,例如 `1A3` 或 `01 02`
- **仅接收 / 仅发送** 可单独看某一方向
- `自动滚动` 取消后表格不会跳到底部,方便你慢慢看某一行
- 右键菜单:`复制所选行` / `载入到发送框` / `清空表格`
  —— 收到一帧不认识的报文,直接"载入到发送框"改几个字节再发回去,是最常用的调试手法

表格默认只保留最近 5000 行(环形缓冲),长时间跑不会把内存吃满。

### 4.4 统计

按 `ID + 方向` 汇总,显示接收数、发送数、平均周期与频率,用于核对 STM32 的定时发送周期是否正确。

> 注意:统计基于**打开通道后**的全部流量,不受监控表的过滤和"清空"影响。

## 4.5 UDS 刷写（读 hex + ISO-TP 多帧）

右侧「分析与刷写 → **UDS 刷写**」标签页。用于把 Intel HEX 固件按标准诊断下载流程烧进 ECU。

### 刷写流程

```
(可选) 前置命令   进编程会话 10 02 / 安全解锁 27 01 xxxx …
        ↓
0x34 RequestDownload      申请下载（地址 + 总长度），ECU 回复最大块长度
        ↓
0x36 TransferData         按块循环，块序号从 1 开始
        ↓
0x37 RequestTransferExit  结束传输
```

### 使用

1. **文件**：选 `.hex`，面板会显示长度、地址范围、记录数。
   - 支持 Intel HEX 的数据类型记录、`04` 扩展线性地址、`01` 结束记录
   - 地址之间的空洞自动用 `0xFF` 填充（跳过的地址通常是已擦除的 flash）
   - 校验和不合法会**直接报错并指出行号**，不会带着坏数据往下走
2. **CAN ID**：默认发送 `0x737` / 接收 `0x736`，按需改。
3. **块大小**：默认**跟随 ECU** —— 收到 `0x34` 正响应后，直接采用 ECU 在
   `maxNumberOfBlockLength` 里声明的值，不再用手动设置。
   - 勾选 **「自动采用 ECU 在 0x34 响应中声明的块大小」**（默认开），下面的输入框会置灰
   - **计数口径**：ISO 14229 没规定 `maxNumberOfBlockLength` 是否包含
     `0x36` + 块序号这 2 字节，各家 ECU 实现不同。默认按**包含**处理（对应勾选项）。
     你实测的 ECU 返回 `74 00 04 02` = 1026 含服务头 → 每块实际数据 **1024 字节**。
     若 ECU 是「仅数据字节」，取消该勾选即可。
   - 若 ECU 声明的值超过 ISO-TP 单消息上限（4095 字节），会自动夹到 **4093**
   - ECU 没声明块长度（响应只有 2 字节参数）或声明值过小时，沿用手动设置并给出提示
   - 想手动指定：取消「自动采用」，在输入框填值；此时若手动值大于 ECU 上限仍会被夹住

   实际生效的块大小会显示在进度条下方，日志里也会逐项打印：

   ```
   -> 74 00 04 02
      ECU maxNumberOfBlockLength = 1026 字节
      该值含 0x36 与块序号 -> 每块实际数据 1024 字节
      采用 ECU 块大小: 1024 字节
      共 5,752 字节 / 每块 1024 字节 = 6 块
   ```
4. **前置命令**：真实 ECU 一般要先进编程会话，必要时还要 `0x27` 安全解锁。
   选预设或手填（`27 01 12 34` 这种写法，多条用逗号分隔）。
   > 安全解锁的密钥算法各家 ECU 不同，这里不做实现，用「附加前置」把算好的请求帧发出去即可。
5. 点 **开始下载**，看进度条与刷写日志。中途可 **中止**。

### ISO-TP 说明

经典 CAN（8 字节帧）下的帧结构，程序按 ISO 15765-2 实现：

| 帧 | 布局 | 数据字节 |
|----|------|---------|
| 单帧 SF | `[0x0N][数据…]` | ≤ 7 |
| 首帧 FF | `[0x1H][LL][数据…]` | 6（PCI 只有 2 字节，**不带序列号**）|
| 连续帧 CF | `[0x2N][数据…]` | 7（**首个 CF 的 N = 1**）|
| 流控 FC | `[0x3F][BS][STmin]` | —（PCI 3 字节，由 ECU 发给本工具）|

要点：

- 流控帧是**接收方（ECU）发出的**，本工具只等不发
- 尊重 ECU 的 **BS**（每多少帧要再要一次流控）和 **STmin**（帧间隔）
- ECU 若回 `FC = Overflow`（要求中止）或 `FC = Wait`（让等），程序会正确处理
- 单帧请求也会包 ISO-TP 头。裸发会被对端误当成 PCI 解析 —— 例如 `0x37` 首字节高半字节是 `0x3`，会被当成流控帧丢掉

### 常见否定响应

失败时日志会给出 NRC 及含义，常见的有：

| NRC | 含义 | 常见原因 |
|-----|------|---------|
| `0x13` | 长度或格式错误 | 块大小超了 ECU 缓冲区 —— 试取消「含服务头」勾选 |
| `0x7F` | 当前会话不支持该服务 | 没先进编程会话就发 0x34 |
| `0x7E` | 当前会话不支持该子功能 | 同上 |
| `0x33` | 安全访问拒绝 | 没做 `0x27` 解锁，或密钥错 |
| `0x35` | 无效密钥 | 密钥算法/种子不对 |
| `0x70` | 上传下载条件不满足 | 没解锁、没擦除、flash 忙 |
| `0x72` | 通用编程失败 | 地址越界、flash 写失败、校验错 |

## 5. 日志格式

### 5.1 CSV

默认写到 `logs/canlog_年月日_时分秒.csv`,UTF-8 BOM 编码(Excel 双击打开不乱码)。

| 列 | 含义 |
|----|------|
| `time` | 本地时间,毫秒精度 |
| `time_s` | Unix 时间戳(秒,6 位小数) |
| `dir` | `RX` 接收 / `TX` 发送 |
| `id_type` | `STD` 标准帧 / `EXT` 扩展帧 |
| `id_hex` | CAN ID,十六进制 |
| `dlc` | 数据长度 |
| `data_hex` | 数据内容 |
| `flags` | 附加标志,如 `RTR` `ERR` `FD` `BRS`,多个用 `|` 分隔 |

示例:

```
time,time_s,dir,id_type,id_hex,dlc,data_hex,flags
2026-10-14 00:09:24.208,1791907764.208855,TX,STD,0x123,4,DE AD BE EF,
2026-10-14 00:09:24.310,1791907764.310012,TX,EXT,0x18FF50E5,2,01 02,
```

### 5.2 BLF

同样时间戳命名的 `.blf`,是 PEAK 官方二进制格式。
用 **PCAN-View** 打开即可回放,收发方向、时间轴、错误帧都能正确还原(方向信息由 BLF 的 DIR 标志记录)。

## 7. 常见问题

**Q: 下拉框里没有设备?**
A: ① 设备管理器里确认 PCAN-USB 状态正常;② 确认装的是 PCAN-Basic 驱动;
③ 点 `刷新` 重新扫描;④ 设备被别的程序(PCAN-View 等)独占时,关掉那些程序。

**Q: 刷写时程序突然消失,没有报错窗口**
A: 这类是**硬崩溃**(退出码 `0xC0000409`),不是 Python 异常,所以不会有 traceback。
已修掉三个已知原因:后台线程直接操作 Qt 控件、运行中的 QThread 被析构、
以及用 `terminate()` 强杀卡在 PCAN 驱动里的线程。
若仍复现,先看 `logs/app.log` 记录到哪一步;若日志停在某一帧后无输出,
优先怀疑 PCAN 驱动或设备接触问题(重新插拔 USB)。

**Q: 刷写没反应,一直卡在某一步**
A: 看「刷写日志」最后一行。若停在 `0x34 之后` 等流控帧,说明 ECU 收到 0x34
但没回 `0x30` 流控帧 —— 检查 ECU 的 ISO-TP 实现是否按 2 字节 PCI 的首帧格式处理,
以及请求/响应 ID 是否配对(本工具默认 `0x737`/`0x736`)。
A: 通道被占用,或者**驱动还没释放完**。常见于刚关闭本工具就立刻重开
(PCAN 驱动释放通道需要一两秒)。程序已经内置自动重试(最多 3 次)来兜这种情况,
偶尔仍失败就等几秒再点一次 `打开通道`,并确认 PCAN-View 等程序已退出。

**Q: 刷写时程序突然消失,没有报错窗口**

**Q: 发送提示失败 / 报 bus-off?**
A: ① 波特率和总线上其它节点不一致;② 接线错误(H/L 接反、没有共地);
③ 终端电阻不对,波形畸变;④ STM32 的 CAN 没初始化或引脚不是复用推挽。

**Q: 能发但收不到 STM32 的报文?**
A: ① STM32 侧过滤器配置成了只接收特定 ID;② STM32 邮箱没被正确填充就启动;
③ 本工具的 `过滤` 框里有残留关键字;④ STM32 只发不循环 —— 用本工具的**周期发送**反证一下:
如果 STM32 也收不到周期帧,问题在 STM32 侧或接线。

**Q: 表格刷太快看不清?**
A: 先点 `暂停`,再点 `清空`,然后取消 `自动滚动`。

**Q: 高总线负载下界面卡?**
A: 表格有 5000 行上限,并且界面刷新做了批量合并(每 60 ms 或每 256 帧推一次),
正常 500 kbit/s 总线不会卡。若确实吃力,可在"记录收发报文"里关掉 BLF(它需要额外做格式转换)。

### 线程模型

- **CAN 工作线程**(`worker.py`):负责 `recv`/`send`、写日志、更新统计、调度周期发送,
  并提供阻塞式 `request()` / `receive()` 供 UDS 做请求-响应。界面卡顿或被拖慢都不影响收发与落盘。
- **界面线程**:只负责画界面。工作线程**不会为每帧发信号**,而是把报文攒成批,
  每 60 ms 或每 256 帧推一次 —— 否则高速总线下信号会把 Qt 事件循环淹没,界面直接假死。
- **刷写线程**(`flash_panel.py` 的 `_FlashThread`):跑 0x34/0x36/0x37 流程。
  刷写期间复用监控用的那条 CAN 总线(PCAN 同一通道不能开两次),所以每一帧
  依然会出现在监控表和日志里,出问题时可以直接回看。
  进度与日志**只经由 Qt 信号**回到界面线程 —— 后台线程直接改 QWidget 是
  未定义行为,高速刷写时会直接闪退(见下)。

### 线程安全的三条铁律

这几条都是踩过坑之后加的,改代码时请一并保持:

1. **后台线程绝不碰 QWidget。**
   进度条、日志、按钮状态一律用 `pyqtSignal` 发回界面线程处理。
   违规表现:刷写中途整个进程闪退,退出码 `0xC0000409`,**没有任何 Python 异常**。

2. **QThread 必须真的结束了才能被析构。**
   运行中的 QThread 被析构会让 Qt 直接 `abort()`。
   所以关闭/关通道的路径都走 `_stop_flash_thread()`,它会 `wait` 到线程真正退出。

3. **不要用 `terminate()` 强杀 CAN 工作线程。**
   它可能正卡在 `PCANBasic.dll` 内部,强杀会踩坏驱动状态,表现为访问冲突闪退。
   现在改为:先 `wake_pending_requests()` 唤醒等待者 → `shutdown_bus()` → 最多等 15 秒。
